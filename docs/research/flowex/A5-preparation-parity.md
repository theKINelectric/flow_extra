# A5 — module initialization parity (FX-007)

Experiment record, pursuit §3 style. Work package A, remainder; consulted with Astra (codex session `01a0e072`, 2026-09-26) before implementation.

- **Claim (Astra's FX-007 ruling):** module `init/1` prepares immutable callback options during explicit pipeline construction, in the starting caller, before any workers start — once per declared occurrence on the sync engine, once per replica on the async engine — and prepared options are reused for every request and for supervisor-driven restarts. Initialization never runs per packet. The sync engine validates declared counts with the same rules and executes one representative per stage.
- **Counterexample (audited revision `1e06223`):** the sync walker called module `init/1` during request processing; the audit probe counted one init on the async track versus two for two calls on the sync track. Sync also skipped the count validator, and a garbage module `init` was only discovered by crashing a caller far from the cause.
- **Regression:** `test/flowex/sync/preparation_parity_test.exs` (+ `test/support/preparation_parity_pipelines.ex`); the sync module-init admission case in `admission_test.exs` was repinned from deferred crash-on-call to startup refusal. RED at `8ed23eb` — 4/9: per-request preparation (3 where 2 belong), error-stage prepared 0 times when healthy, no count refusal, no startup refusal.
- **Fix:** `Flowex.PipelineBuilder.prepare_stages/2` is the sync engine's single preparation entry point, and the async builder's topology walk shares the same lower-level helpers (merge, module-option preparation, kind resolution) while keeping its per-replica preparation. Preparation validates pipeline opts, validates the whole declaration (counts) before any module initializer runs, merges pipe opts, runs module `init/1` + validation, and returns prepared `Flowex.StageOpts` entries (function stages carry `{pipeline_module, atom}`, module stages `{module, :call}`). Both sync entry points prepare caller-side; `Flowex.Sync.Supervisor` receives the prepared list and bakes it into the child spec; the sync walker's state is the prepared list — no per-request init or merging, and function/module error handlers unify into one three-argument dispatch. The contract is user-facing documentation (`Flowex.Pipeline` moduledoc and README).
- **Strengthened evidence (Astra's completion review):** token instruments observe the law four ways — engine-tagged preparations arrive before any request exists, from the starting caller's process, three tokens for three async replicas against one sync occurrence, and requests plus restarts provably run on the startup-minted tokens with no new preparation. The whole declaration is validated before any initializer runs, so a refused start leaves no half-prepared side effects.
- **Parity boundary (stated, per the consult):** for deterministic option preparation and callbacks, both engines agree on option precedence, struct conversion, callback order within a packet, error routing, and resulting data. Process identity, replica-local values, concurrency, and initialization invocation counts need not match. `init/1` is configuration preparation, not a worker resource lifecycle callback.
